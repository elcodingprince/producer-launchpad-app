Producer Launchpad Operations Map

Multi-merchant delivery with one repo, many app identities, and one shared database.

This document maps the intended custom-distribution fleet: each merchant gets a dedicated Fly app and Shopify custom app identity, while Neon Postgres remains the shared system of record.

System Map

One codebase produces one release. That release fans out to merchant-specific Fly apps. Those Fly apps use merchant-specific Shopify credentials but point to the same Neon database.

Producer Launchpad repo Shared source code, Prisma schema, migrations, extensions, Dockerfile, and deployment scripts.
Release foundation Build image once, run database migration once, then deploy the same version to every merchant app.
Merchant fleet Each merchant gets its own Fly app and Shopify custom app identity. All merchant data is scoped by shop in Neon.

Release Workflow

This is the target path for pushing an update to ten merchants without corrupting the shared database or accidentally running ten migrations.

1

Build one release

Cut a Git commit or tag and build one Docker image. Every merchant should receive this exact same image.

2

Create recovery path

Create or confirm a Neon branch, backup, or point-in-time restore window before running risky migrations.

3

Migrate once

Run npm run db:migrate:shared once against the shared Neon production database.

4

Deploy the fleet

Deploy the same image to every merchant Fly app using the merchant registry as the source of truth.

5

Smoke test each app

Check app boot, Shopify auth, a protected admin route, webhook reachability, and one merchant-specific data read.

Database Update Rules

App deploys do not replace the live database. Migrations update the database structure in place while preserving existing rows unless the migration explicitly deletes or rewrites them.

Safe default

Additive migrations are the normal path: add a table, add a nullable column, add an index, backfill data, then deploy app code that uses it.

Use care

Destructive migrations need a staged plan: expand schema first, backfill, deploy compatible code, verify, then remove old columns later.

Change type
Risk
Recommended handling
Add new table
Low
Create migration, run once, deploy app code that writes/reads the table.
Add nullable column
Low
Apply migration first, then deploy code that starts using the column.
Add required column
Medium
Add as nullable or with default, backfill existing rows, then enforce required behavior later.
Rename or drop column
High
Use expand-and-contract: add replacement, dual-read/write if needed, backfill, verify, then remove old field in a later release.
Tenant-scoping change
High
Add shop, backfill from related parent rows, add indexes, update all queries to include shop.
